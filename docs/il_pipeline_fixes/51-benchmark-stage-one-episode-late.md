# 51 — Benchmark stages on the same map ran one episode late

**Status:** Fixed · **Repo(s):** arena-rosnav · **Files:** `task_generator/task_generator/tasks/modules/benchmark.py`, `task_generator/task_generator/task_config.py` (new), `task_generator/scripts/filewatcher.py`, `task_generator/task_generator/tasks/task_factory.py`, `task_generator/task_generator/task_generator_node.py`, `task_generator/task_generator/constants.py`, `arena_bringup/launch/start_trials.launch`, `task_generator/test/test_benchmark_stage_timing.py` (new), `test_double_resume.py`, `test_benchmark_il_record.py`, `test_filewatcher_config_file.py`
**Behaviour change:** With `tm_modules:=benchmark`, a stage's config is used from the stage's first episode on, a run no longer starts one extra reset after the last episode, and a change of `tm_robots`/`tm_obstacles` between stages relaunches. Every launch: at each reset the task modes get the server's current config if it changed.

## Problem
A reset runs `before_reset` of the modules, places robots and obstacles from the task config, then runs `after_reset` (`task_factory._reset_task`). The benchmark counted episodes in `after_reset`. When a stage's episodes were used up it switched to the next stage and wrote that stage's config, but the reset that starts the new stage had already placed everything from the old config. Stages that change the map relaunch and were not affected; stages on the same map ran one episode late: the first stage got one extra episode, every following stage ran in its predecessor's slot, and the last stage's scenario never ran.

Seen on 2026-10-26, `il_dataset_small_v1` (CS1–CS4, one episode each, `gru_learn`): the episodes were CS1, CS1, CS2, CS3 (start, goal, pedestrian spawn points and static obstacles in the scan all match those files), the benchmark log reported stages 1–4. Every suite with several stages on one map is affected (50ped_daniel, the IL suites), including all sessions marked preliminary.

A second, smaller gap: the written file reaches the task modes asynchronously (filewatcher → `task_generator_server` → reconfigure callback of each task mode). Moving the count alone would leave a window in which a reset still reads the old scenario.

## What changed
- `Mod_Benchmark.before_reset` counts the episode (and so switches stage and writes its config) before the reset places anything; `after_reset` does nothing.
- The stage's `timeout` is part of that config. Before, only a relaunch passed it (`timeout:=`), so stages on the same map kept the first stage's timeout (`il_dataset_small_v1`: 90 s for every stage, 120 s intended from smartgap on). A stage without `timeout` gets the run's: the launch's `timeout:=` (param `benchmark_run_timeout`, set by `start_trials.launch`; the server's own param can already hold a stale file's value; other launch files: the server's param) at the first launch, kept in the resume lock file (5th field) through relaunches (an older 4-field lock file: the relaunch's) (it used to take `Config.Robot.TIMEOUT` when the suite was parsed, often still `inf`, which also entered the stage's default seed).
- The stage's config is overlaid on the backup and written once (`_taskgen_write(..., base=)`, which returns it), instead of restoring the backup and then writing.
- Without a relaunch, `_reincarnate` then sets that whole config on `task_generator_server` itself with a blocking `update_configuration` (`_apply_task_config`), so the server holds it before the reset continues; the filewatcher applies the same file later. A failure is logged as an error. The first reset after a (re)launch does the same with the written file, since the filewatcher may not have applied it yet.
- The evaluation recorder (`change_directory`) still moves to the new stage's folder in `after_reset`, once the reset has placed everything; moved to the stage change it recorded the reset into the new stage as an extra episode 0.
- A stage start restarts the RNG from the written config's seed (`constants.reseed`; the stage's, or `RANDOM.seed` if its config sets one), also when the previous stage had the same seed (paired stages draw the same). If the config cannot be applied (server unreachable), the benchmark does nothing more and the whole launch stops (as at the end of a run; the lock file stays) with a fatal error and `STAGE CONFIG NOT APPLIED` in the benchmark log: the filewatcher would apply it at some point during the stage.
- The config-to-parameter mapping moved from the filewatcher into `task_generator/task_config.py` (`task_config_params`), used by both; lists of numbers are now encoded too (`;`-joined strings).
- `CombinedTask._reset_task`, after the modules' `before_reset`, gives the robot and obstacle task modes the server's current config (`_sync_task_config`) when it changed since the last reset: their reconfigure callbacks are asynchronous. This holds for every task mode. A task mode that fails to load it logs an error and keeps its config, as when the callback fails. The same config goes to `constants.reconfigure` (RNG from `RANDOM_seed`, timeout, goal tolerance, episodes), which also runs as the server's callback; between stage starts it recreates the RNG only when `RANDOM_seed` changes, because the config arrives more than once (benchmark, filewatcher, this sync) and recreating it partway through a stage restarted the random sequence (a random stage's second episode could repeat its first).
- When a module ends or restarts the run in `before_reset` (benchmark completed, relaunch), no further module runs, nothing is placed, and the node publishes no `/scenario_reset`, so no episode is started in the old stage's recordings. Nothing more is sent to the stopped master (`/reset_end`, the `resetting` parameter), which raised a connection error in the reset thread.
- A change of `tm_robots` or `tm_obstacles` between stages now relaunches, like a map or robot change: task modes are launch parameters, and without a relaunch the old one kept running.

## Effects
- `il_session_recorder` writes each episode's `timeout` into `episodes.csv`; `il_check_session` judges TIMEOUT with the episode's timeout.
- Each stage runs its own scenario, with its episode count. The benchmark log (`S`/`E` lines) now matches what ran.
- A run no longer starts one more episode after the last one before it ends.
- Each reset reads the server's parameters once (one master call).
- The global RNG is no longer recreated when an unchanged config is set again (also from rqt_reconfigure); it was before.
- Not changed: the config file is still written in place (not atomically), as before. Top-level parameters missing from the base config (`goal_radius`, `goal_tolerance_angle`) keep the value an earlier stage set, as with the filewatcher before; no suite sets them, and `goal_radius` is read by the robot manager only at startup anyway.

## Test
`task_generator/test/test_benchmark_stage_timing.py`: the scenario active at each reset for stages of 1/1/1/1 and 2/1/3 episodes (fails on the old code with `0.json` twice); the config written once onto the base; the whole written config (base values included) applied with `update_configuration`, a failure reported; a task-mode change requires a relaunch; `task_config_params` (names, lists, dicts); `_sync_task_config` (applies a changed config once, a failing task mode keeps its config, runs after the modules and before placement, no further module and no placement after a module ended the run, nothing sent to the master after that, `Config` synced before the task modes); the stage timeout in the written config and `timeout:=` (the run's without one, kept in the lock file); the evaluation recorder moved after the reset; the config applied and the RNG restarted at a stage start (from a seed the stage config sets; the run stops when applying failed) and at the first reset after a relaunch; `constants.reconfigure` keeps the RNG for an unchanged seed, `constants.reseed` restarts it. `test_double_resume.py`: no `/scenario_reset` when the run ended in the reset.

End to end (2026-10-26, master 11312, no display, planner driving): suite CS1 ×1, CS2 ×2, then a stage with `tm_obstacles: random` (4 pedestrians, 2 static). At each `/scenario_reset` the server held CS1, CS2, CS2 and the pedestrians spawned at those files' positions; the random stage relaunched ("task mode change requires restart") and ran 4 random pedestrians; no "task config not applied" error; the run completed after the fourth episode.
